## Multi-channel audio architecture and ownership

`ApplicationAudioRuntime` remains one module-level singleton. It lazily creates one AudioContext and one shared master gain. Every stable `ChannelId` owns an independent branch:

`SINE SOURCE -> SOURCE ENVELOPE -> CHANNEL GAIN -> CHANNEL ANALYSER -> SHARED MASTER -> DEVICE`

The AudioContext/master are application-owned. Oscillator, envelope, analyser, gain, frequency, level, active state, error state, and cleanup are channel-owned. Starting or disposing a channel never recreates or closes shared infrastructure. Only `shutdownApplication()` may close the AudioContext.

The five-channel fixture is created through the existing dynamic reducer/UI path. No fixed collection of five audio objects exists and there is no five-channel maximum.

## Identity, oscillator, and independent controls

Runtime branches are held in a `Map<ChannelId, ChannelAudioInstance>`, never by UI index. Deleting CH 02 therefore cannot transfer CH 03 state when visible arrays close the gap. Replacement identities use the reducer's existing max-active-plus-one policy.

Every channel gets the same sine-only controls and its own source lifecycle. Dynamic default frequencies use a formula based on stable numeric identity: CH 01–06 begin at 78, 110, 156, 221, 312, and 441 Hz. The formula is a recognisable test aid, not a fixed fixture or capacity limit. Frequency and level updates address only the keyed channel branch and never create a source.

## Headroom and summing safety

The existing conservative fixed-gain strategy remains appropriate for this test: maximum channel gain is 0.2, shared master gain is 0.8, and default channel level is 20%. Five phase-aligned channels at their maximum UI level have a theoretical peak sum of 0.8; at defaults the theoretical sum is 0.16. No limiter, compressor, effects, dynamic normalisation, or mastering chain was added. Fixed headroom also avoids changing already-running peers when another channel starts or stops.

Listening must still begin at conservative device/headphone volume. Automated tests do not establish perceived loudness, clipping, or hearing safety.

## Active deletion, synchronization, and resource cleanup

The Remove Channel action disposes that exact runtime branch before reducer removal. `synchronizeChannels()` also reconciles runtime/configuration identities with `AppState.threadChannels`, so clear/reset/preset state replacement cannot leave a stale oscillator branch. Scoped disposal stops only that source, disconnects only that analyser/gain, clears only that channel configuration/error, and retains context/master and peers.

Diagnostics now include context creations, active channel branches, channel creations/disposals, analyser creations/disposals, source creations/disposals, and active sources. Repeated unit/browser lifecycle tests use these counters to prove no unexpected master/source creation and correct branch cleanup.

## Monitor and analyser strategy

Monitor resolves the current stable channel from direct channel selection, the selected source module's channel terminal, or the first channel when nothing is selected. Its identity, frequency, level, active state, message, and waveform all come from that channel snapshot/analyser. Rapid selection changes only the observer target and never starts, stops, or reconstructs sources.

Each active channel retains one lightweight analyser (`fftSize = 512`) as part of its isolated branch. Only the currently focused Monitor performs `requestAnimationFrame` waveform reads; hidden/unfocused channels have no user-facing render loop. The waveform remains real time-domain audio data, not decoration.

## Navigation and spatial boundary

Multiple sources intentionally continue through Threads -> Sound Desk -> Visualiser -> Threads. The browser test verifies context/master/channel/source creation counters and active-source count do not change across navigation. X/Y routing remains application state only. No pan, Y processing, spatial stage, Blend, module processing, recording, sample playback, or simulation work was introduced.

## Regressions discovered/fixed

No approved functional regression was found in the final gate. The implementation removed the former CH 01-only UI/Monitor/waveform assumptions and added reducer-to-runtime cleanup so non-button channel resets cannot strand audio.

## Current visual-wiring compatibility with future single-input / Blend semantics

Channel output terminals already accept only one visual source connection. Ordinary module inputs can currently display more than one committed Thread because the prototype validator rejects duplicate source-target pairs but does not reserve an input after its first connection. No real audio graph is derived from those visual Threads in Milestone 08, so hidden summing was not introduced. Before processing modules become audible, module semantics must either enforce one resolved stream per ordinary input or route explicit two-input combinations through the future Blend module. Milestone 08 deliberately does not redesign the visual graph or implement Blend.

## Known limitations and Milestone 09 concerns

- Spatial coordinates are acoustically inert and every channel remains centred.
- Fixed headroom is proven mathematically only for the five-channel fixture at current gain limits; this milestone is not an overload/capacity study.
- Per-channel analysers are intentionally small, but larger populations should be measured before assuming negligible cost.
- Browser/device-specific clicks, latency, clipping, and perceived loudness still require user listening.
- Audio configuration remains runtime-local and is not part of durable project persistence.
- Milestone 09 must add pan as a channel-owned stage before the shared master without changing context/master ownership or allowing Monitor/navigation to own sources.
